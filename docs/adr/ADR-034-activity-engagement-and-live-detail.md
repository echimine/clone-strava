# ADR-034: Kudos list, comments and live updates on the Activity detail

- **Status**: accepted
- **Date**: 2026-10-16
- **Deciders**: echimine
- **Tags**: engagement, kudos, comments, realtime, activities, mobile, ios, api

## Context

[ADR-033](ADR-033-activity-detail-edit-delete.md) adds the Activity detail. Its engagement part is missing: the card counts comments but there is no comment screen (`FeedView` "TODO(ADR-029): open the comments screen"), there is no way to see who gave kudos, and nothing on the detail updates while it is open.

The decisions were worked out in the same grilling session as ADR-033 (2026-10-16). The facts they depend on, from the code at `f45b452`:

- `engagement.comment` exists: `id uuid PK, activity_id (cascade), user_id (cascade), body text, created_at, deleted_at`, with a partial index `(activity_id, created_at) where deleted_at is null`. **No `updated_at`.** `CommentRepository.add` and `AddCommentUseCase` are stubs; there is no comment endpoint. Comment counts already exclude deleted comments.
- Kudos: `PUT` / `DELETE /v1/activities/:id/kudos`, `422 cannot_kudos_own_activity` (ADR-029 §5). No list endpoint. No engagement domain events.
- Realtime (ADR-010): plain WebSocket, a 60 s token whose `topics` claim is fixed when it is issued, only `user:{userId}` today, IDs-only payloads, at-most-once delivery with resync on reconnection. ADR-010 §4 already foresees "`activity:{id}` for live comments" and §1 forbids the gateway any database access.
- There is **no username or handle**, no athlete profile (endpoint or screen), no follows, no notifications (no `device` table, APNs postponed by ADR-006 and ADR-011).

## Decision

### 1. Kudos on the detail

- The detail shows the count, the kudos button (hidden on the viewer's own Activity, which cannot receive their kudos) and a row of up to **5 avatars** of the most recent kudos. Tapping the row opens a sheet with the full list.
- **`GET /v1/activities/:id/kudos?cursor=&limit=`** (1–50, default 20): `{ items: [{ athlete {id, displayName, avatarUrl}, givenAt }], nextCursor }`, most recent first, keyset on `(created_at desc, user_id)`. Not visible: `404 activity_not_found`. Identities are assembled in `apps/api` as in the feed (ADR-029 §2).
- Athletes in the list are not tappable (no athlete profile).

### 2. Comment model (amends ADR-017)

- New column **`comment.updated_at`** (`timestamptz`, nullable), set on each edit. A comment is shown as "modifié" when it is not null.
- The comment **id is generated by the app**, like an Activity's (ADR-008 §4), so an optimistic send can be replayed and the realtime echo recognised.
- `body`: plain text, trimmed, **1–1,000 characters**. No markup, no mentions.
- Deletion stays a soft delete (`deleted_at`, ADR-017). A deleted comment is never returned and is not shown (no "comment deleted" placeholder).
- **Mentions, later**: they will live in a separate `comment_mention (comment_id, user_id, offset, length)` table written alongside the body, so the body stays plain text and existing comments need no migration.

### 3. Comments API

All routes first check that the viewer can see the Activity (`getVisibleActivity`), else `404 activity_not_found`; comments are only accepted on `processed` Activities (`409 activity_not_commentable` otherwise, which only the author can hit).

| Route | Who | Behaviour |
|---|---|---|
| `GET /v1/activities/:id/comments?before=&limit=` | anyone who sees the Activity | The newest page (default and max **50**) in **chronological order**; `before` is an opaque cursor on `(created_at, id)` to load older comments; `previousCursor: null` when there are none. Items: `id, body, createdAt, updatedAt, author {id, displayName, avatarUrl}, viewerCanEdit, viewerCanDelete` |
| `GET /v1/activities/:id/comments/:commentId` | same | One comment, `404 comment_not_found` if unknown or deleted (used by the realtime handling of §5) |
| `POST /v1/activities/:id/comments` `{ id, body }` | anyone who sees the Activity | `201` with the comment. Same id by the same author on the same Activity: `200` with the existing comment (replay). Id used by someone else or on another Activity: `409 comment_id_conflict`. *Amended 2026-10-17 (review of #88/#89)*: replaying the id of a comment its author has since deleted is also `409 comment_id_conflict` (the deleted comment is never returned, §2) |
| `PATCH /v1/activities/:id/comments/:commentId` `{ body }` | the comment's author only (`403 not_comment_author`) | `200` with the comment, `updated_at` set. No time limit |
| `DELETE /v1/activities/:id/comments/:commentId` | the comment's author **or** the Activity's author (`403` otherwise) | Soft delete, `204`; already deleted: `204` (idempotent) |

- The `engagement` use cases implement the rules; author identities are assembled in `apps/api`.
- `viewerCanEdit` = viewer is the comment's author; `viewerCanDelete` = viewer is the comment's author or the Activity's author.
- The detail's `engagement.commentCount` (ADR-033 §2) is the count of non-deleted comments, as in the feed.

### 4. Domain events (amends ADR-021 §5)

Emitted by `engagement` after the commit, IDs only (ADR-021 §3):

| Domain event | Payload |
|---|---|
| `engagement.comment.added` | `{ commentId, activityId, userId }` |
| `engagement.comment.edited` | `{ commentId, activityId, userId }` |
| `engagement.comment.deleted` | `{ commentId, activityId, userId }` |
| `engagement.kudos.given` / `engagement.kudos.removed` | `{ activityId, userId }` |

A replayed `POST` (`200`) or a repeated `DELETE` emits nothing. `PUT` / `DELETE` kudos emit only when the state actually changed.

### 5. Realtime: the `activity:{id}` topic (amends ADR-010 §3, §4, §5 and ADR-021 §4, §5)

**Subscription grant.** The token fixes topics at connection time, but which Activity will be opened is only known later, and the gateway may not read the database (ADR-010 §1). So the API signs a per-topic grant:

1. On opening the detail, the app calls **`POST /v1/realtime/grants`** `{ topic: "activity:{id}" }`. The API checks the topic format and that the viewer can see the Activity (`getVisibleActivity`; `404` otherwise), then returns `{ grant, expiresInS: 60 }`: an HS256 JWT signed with `REALTIME_TOKEN_SECRET`, claims `{ sub, topic, iss: clone-strava-api, aud: clone-strava-realtime-grant }`, valid 60 s. The distinct audience means a grant can never be used as a connection token.
2. The app sends `{ a: "sub", topic, grant }` on its existing connection.
3. The gateway accepts the subscription if the topic is in the connection token (as today) **or** the grant verifies locally (signature, algorithm, issuer, audience, expiry) with `topic` equal to the requested topic and `sub` equal to the connection's user. Otherwise `sub:err forbidden`. The existing quota (20 topics per connection) applies.
4. The app sends `{ a: "unsub", topic }` when the detail closes. On every reconnection it asks a fresh grant for the detail still open, then reloads the detail and its comments (catch-up, ADR-010 §7).

`packages/realtime` gains `activityTopic(id)`, the grant claims schema and the optional `grant` field of the `sub` message.

**Forwarding table** (bridge, ADR-021 §4):

| Domain event | Mobile event | Topics | Payload |
|---|---|---|---|
| `engagement.comment.added` | `comment.created` | `activity:{activityId}` | `{ activityId, commentId }` |
| `engagement.comment.edited` | `comment.updated` | `activity:{activityId}` | `{ activityId, commentId }` |
| `engagement.comment.deleted` | `comment.deleted` | `activity:{activityId}` | `{ activityId, commentId }` |
| `engagement.kudos.given` / `removed` | `kudos.changed` | `activity:{activityId}` | `{ activityId }` |
| `activities.activity.updated` | `activity.updated` | `user:{userId}` (ADR-033 §8) **and** `activity:{activityId}` | `{ activityId, changedFields }` |
| `activities.activity.deleted` | `activity.deleted` | `user:{userId}` **and** `activity:{activityId}` | `{ activityId }` |

**App handling** (the detail only; the feed is not subscribed to other athletes' Activities):

- `comment.created` / `comment.updated`: ignored if the comment is already known with the same state (the echo of the viewer's own send or edit); otherwise `GET` that comment and insert or replace it.
- `comment.deleted`: remove it locally.
- `kudos.changed`: reload the detail's engagement (count, `viewerHasKudoed`, avatar row).
- `activity.updated`: reload the detail; a `404` switches to the unavailable state (ADR-033 §3), e.g. when it became private.
- `activity.deleted`: unavailable state, then `unsub`.

**Revocation**: a grant is only checked at subscription time. A viewer who loses access (Activity made private) keeps the subscription until they leave or reconnect, but only receives IDs: every reload goes through the API, which refuses with `404`. Accepted, as the payloads reveal nothing.

### 6. iOS

- **Layout**: under the stats (ADR-033 §3), the kudos block, then the comments in chronological order with "Voir les commentaires précédents" at the top when `previousCursor` is set, and a **composer pinned to the bottom** of the screen. Opening the detail from the card's comment button scrolls to the comments and focuses the composer.
- **Sending is optimistic**: the comment appears at once, greyed, with "Envoi…", using its app-generated id; on failure it shows "Échec · Réessayer" and keeps its text; retrying replays the same `POST`.
- **Long press on a comment**: "Modifier" and "Supprimer" on my comments, only "Supprimer" on others' comments when I am the Activity's author. "Modifier" loads the text into the composer with a "Modification… ✕" banner; sending issues the `PATCH`. "Supprimer" asks for confirmation.
- **Edits and deletes** are optimistic too, rolled back with a toast on failure (same rule as ADR-033 §7).
- **Feed counts**: the comment and kudos counts changed on the detail reach the card through ADR-033 §7's change stream when the athlete comes back.
- Athletes (comment authors, kudos list) are not tappable.

### 7. Out of scope

Mentions, handles, athlete profiles and tappable athletes (§2 keeps room for mentions); follows (until they exist, in practice only the author comments on their own Activities); push and in-app notifications; comment moderation in the backoffice; replies and reactions on comments; live updates in the feed; PostHog events for kudos and comments; photos on comments.

## Alternatives Considered

| Option | Why not |
|---|---|
| Reconnect with a new token listing `activity:{id}` on each detail | Drops and reopens the connection at every navigation and can lose `user:` events during the switch |
| Gateway checks visibility itself | Breaks ADR-010 §1 (no database, no business logic in the gateway) |
| Publish comment events on the `user:` topics of the Activity's author and commenters | Misses a viewer who reads without commenting |
| Full comment in the realtime payload | Two data paths for the app; ADR-010 §5 keeps the API as the single source |
| Comment screen or sheet separate from the detail | One more navigation level; the Strava-like inline thread keeps the Activity in view |
| Mentions now, with a new handle | Nobody to mention (no follows), nowhere to go when tapping one (no profile), nobody notified (no push) |
| No comment editing | Asked for explicitly; the cost is one column and one route |
| Hard delete of comments | ADR-017 keeps soft delete for comments (moderation history) |

## Consequences

### Positive
- The engagement thread works end to end on one screen, live for everyone watching it.
- The grant mechanism adds topics without touching the connection, the token or the gateway's statelessness, and serves any future per-resource topic.
- Optimistic sends with app-generated ids are replay-safe and deduplicate the realtime echo for free.

### Negative / Risks
- **Unused social surface**: without follows, other athletes cannot see each other's Activities, so comments by others and live updates for other viewers cannot be tried for real until follows exist.
- **Revocation lag** on a subscription (§5), limited to IDs.
- **One `GET` per realtime comment event**: fine at the expected volume; a busy thread would need batching.
- **No notifications**: an author only learns about a comment by opening the Activity.
