# ADR-025: Mobile testing strategy — Swift Testing/XCUITest tiers and a CI gate

- **Status**: accepted
- **Date**: 2026-09-25
- **Deciders**: echimine
- **Tags**: testing, swift-testing, xcuitest, ci, mobile

## Context

ADR-007 (mobile architecture) already contains a one-paragraph, table-shaped testing convention — Swift Testing for domain/use cases/services/GRDB repositories/API repositories/stores, XCUITest for "a few" critical flows like recording — but it names tools without a full strategy: no test-target structure, no mocking conventions beyond "fakes," no coverage expectations, no CI. `apps/mobile/StravaCloneTests` already exists and is wired into the shared Xcode scheme (`codeCoverageEnabled = YES`), with exactly one real test file, `CoordinateTests.swift`, using Swift Testing (`import Testing`, `@Test`, `#expect`) — confirming ADR-007's tool choice is already in active use, not just a paper decision.

ADR-005 (monorepo) flags that `apps/mobile` sits outside the pnpm/Turborepo pipeline as a native Xcode/Swift Package Manager project and that "CI must handle [pnpm/Turbo and Xcode] separately" — but never solves it. The only CI workflow in the repo, `.github/workflows/deploy.yml` (ADR-018), is entirely web/backend: it builds and deploys the four Docker apps and contains zero references to `xcodebuild`, `ios`, `swift`, or `mobile`. Mobile CI is unaddressed by any prior ADR.

This ADR formalizes and expands ADR-007's testing table into a full strategy (test target structure, mocking conventions, an XCUITest target, coverage expectations) and decides, for the first time, how mobile tests run in CI. It is scoped to `apps/mobile`. It does not cover the backend (ADR-024) or repo-wide CI orchestration beyond what's needed to add a mobile job.

## Decision

### 1. Tools: Swift Testing for unit tests, XCUITest for critical E2E flows — as ADR-007 already named, now with structure

Both are native to Xcode/Swift; nothing new is added as a dependency, consistent with ADR-006/007's stated philosophy of favoring Apple's native frameworks and limiting third-party dependencies to those that bring real value. No SnapshotTesting, ViewInspector, or Quick/Nimble is added by this ADR — if SwiftUI snapshot testing becomes needed later, that is its own decision with its own ADR, not folded into this one by default.

| Target | Tool | Approach |
|---|---|---|
| Domain, use cases, services | Swift Testing | Fake repositories and fake `LocationProvider`, per ADR-007 |
| GRDB repositories | Swift Testing | In-memory SQLite database, real migrations |
| API repositories | Swift Testing | Mocked `URLProtocol` |
| Stores | Swift Testing | Mocked services and use cases, state assertions |
| Critical flows (recording, auth) | XCUITest | A handful of scenarios, simulated GPS via MobileBuildMCP's location tooling where needed |

### 2. Test target structure: one unit target today, add an XCUITest target now

`StravaCloneTests` (`com.apple.product-type.bundle.unit-test`, bundle id `fr.echimine.stravaclone.tests`) already exists and covers the Swift Testing tier — new unit tests are added here, mirroring `StravaClone/Features/<Name>/...`'s folder structure so a test's location maps directly to the source it covers (e.g. `StravaCloneTests/Features/Recording/Domain/...`).

No XCUITest target exists yet, despite ADR-007 naming XCUITest for critical flows. This ADR adds one: `StravaCloneUITests` (`com.apple.product-type.bundle.ui-testing`), scoped at first to the two flows ADR-007 and ADR-022 call "critical" — activity recording (start → GPS points recorded → stop → activity created, per ADR-008's state machine) and the auth flows this repo just shipped (sign-up/sign-in, per ADR-022) — not a broad UI regression suite.

Because `apps/mobile/StravaClone.xcodeproj` is generated by XcodeGen and gitignored (`project.yml` is the committed source of truth, per ADR-005), any new test target is added by editing `project.yml`'s `targets:` block and regenerating (`xcodegen generate`), never by hand-editing the generated `.pbxproj`.

### 3. Mocking conventions: fakes at the `Domain` boundary, not a mocking framework

Consistent with ADR-002/007's hexagonal boundary (`Domain` depends on nothing but stdlib; a `UseCase`/`Service` depends on a `Domain`-level protocol, never a concrete `Infrastructure` type), a test fakes the protocol, not the framework:
- `LocationProvider`, API repository protocols, and any other `Domain`-level interface get a hand-written fake struct/class conforming to the same protocol — no mocking library, no runtime interception.
- GRDB repository tests use a real in-memory `DatabaseQueue`/`DatabasePool` with the real `DatabaseMigrator` run against it, not a fake — the GRDB layer's own correctness (queries, migrations) is exactly what needs to stay real to be worth testing.
- API repository tests mock at the `URLProtocol` layer (intercepting `URLSession` requests/responses), not by faking the repository's own interface — this exercises the real `URLSession`-based networking code, only stubbing the actual network call.

A shared `StravaCloneTests/TestSupport/` folder holds reusable fakes (`FakeLocationProvider`, a `URLProtocol` stub helper, an in-memory GRDB factory) so each feature's tests reuse one fake per collaborator instead of redefining it per test file — mirroring `apps/api/src/auth/test-auth-app.ts`'s role as a shared bootstrap helper on the backend side (ADR-024 §2).

### 4. CI: a macOS GitHub Actions runner, gating merges to `main`

Add a `mobile-test` job (either in a new `.github/workflows/mobile-ci.yml` or a job within an expanded `deploy.yml`, matching whatever job-split ADR-024 §5's backend test job lands on) that:
1. Runs on a macOS GitHub Actions runner (`macos-14` or later, matching the mobile-team's current Xcode version).
2. Regenerates the project from source of truth (`xcodegen generate`, since the `.xcodeproj` is gitignored).
3. Runs `xcodebuild test -project apps/mobile/StravaClone.xcodeproj -scheme StravaClone -destination 'platform=iOS Simulator,name=<simulator>,OS=<version>'` against both `StravaCloneTests` and the new `StravaCloneUITests` target.
4. Fails the workflow on any test failure.

This job is scoped to pull requests and pushes touching `apps/mobile/**` (a path filter), not every push to the monorepo — a change to `apps/api` alone should not spin up a macOS runner. Unlike the backend (ADR-024 §5), there is no existing mobile deploy pipeline this gates today (ADR-018 covers only the four backend Docker apps) — this job's only job is to fail loudly on a broken build/test, not to gate a release step that doesn't exist yet; wiring an actual mobile release pipeline (TestFlight, App Store) is out of scope here and left to a future ADR.

**Status as of this ADR's last update: this CI job is not implemented yet** — `.github/workflows/` only has `deploy.yml` (backend/web). Tests run locally in the meantime, via the root `package.json` scripts (outside the pnpm/Turbo pipeline per ADR-005, plain `xcodebuild` wrappers):

```bash
pnpm mobile:test      # StravaCloneTests (Swift Testing unit tests) — no backend required
pnpm mobile:test:ui   # StravaCloneUITests (critical flow XCUITest) — requires the dev backend running:
                       #   pnpm db:up && pnpm --filter api dev
```

Both regenerate the Xcode project first (`xcodegen generate`, since `.xcodeproj` is gitignored) and target the `iPhone 17` simulator by default — pass a different `-destination` directly to `xcodebuild` for another device.

### 5. Coverage: no hard threshold, `codeCoverageEnabled` stays on

The scheme already has `codeCoverageEnabled = YES`. This ADR keeps coverage collection on (useful signal, visible in Xcode and in CI logs) but sets no minimum percentage gate, for the same reason ADR-024 §"Negative/Risks" declines one on the backend: a coverage percentage is a separate, disputable decision, and enforcing one now — on a codebase where most `Features/*` subfolders are still `.gitkeep` placeholders — would either be trivially met by testing nothing meaningful or block feature work outright. Revisit once more features are built out.

## Alternatives Considered

| Option | Pros | Cons | Verdict |
|---|---|---|---|
| XCTest (old-style `XCTAssert`) instead of Swift Testing | More historical documentation/StackOverflow coverage | Already superseded in this codebase (`CoordinateTests.swift` uses Swift Testing); ADR-007 already chose it; re-litigating would contradict working code | Rejected |
| Add SnapshotTesting (pointfreeco) now for SwiftUI views | Catches visual regressions XCUITest/unit tests miss | No current need identified; contradicts ADR-006/007's "favor native, minimal third-party deps" precedent until a concrete pain point justifies it | Rejected (deferred, not permanently ruled out) |
| Broad XCUITest suite covering every screen | Higher confidence per screen | Slow, flaky-prone (XCUITest's known weakness), and directly contradicts ADR-007's own "a few scenarios" framing | Rejected |
| No CI for mobile (keep it local-only, like today) | No new workflow to build/maintain, no macOS runner cost | Leaves the exact gap ADR-005 named three ADRs ago and never closed; a broken mobile build could merge to `main` silently | Rejected |
| Run mobile CI on every push, unfiltered | Simpler workflow file (no path filter) | Wastes macOS runner minutes (the expensive GitHub Actions runner tier) on every unrelated backend change | Rejected |

## Consequences

### Positive
- ADR-007's testing table stops being the only word on mobile testing and becomes one section of a full decision — test target structure, mocking conventions, and CI are now explicit instead of left to whoever writes the next feature to improvise.
- The `StravaCloneUITests` target closes a real gap: ADR-007 named XCUITest for critical flows two ADRs ago, and no such target existed until this one.
- Mobile joins the backend (ADR-024) in having a CI test gate — closing the "CI must handle them separately" problem ADR-005 named without ever following through on.

### Negative / Risks
- **macOS GitHub Actions runners are markedly more expensive/slower than Linux runners** — the path-filtered scoping (§4) limits this to mobile-touching changes, but as `apps/mobile` grows past its current mostly-scaffolded state, this job's runtime and cost will grow with it.
- **XCUITest is inherently more flaky than unit tests** (simulator timing, animation waits) — keeping the target deliberately small (two flows, per §2) is a mitigation, not a guarantee; a flaky `StravaCloneUITests` run blocking CI is a real risk to watch for once it's running regularly.
- **Simulated GPS for the recording E2E test is a real technical gap**: XCUITest on a simulator cannot produce genuine GPS movement the way a physical device does. MobileBuildMCP's location-simulation tooling is the intended mechanism (referenced in §1), but the exact mechanics of driving it from an `xcodebuild test` CI run (vs. an interactive MCP session) are not fully worked out by this ADR and may need a follow-up decision once the recording XCUITest is actually written.
- **No coverage threshold** means this ADR's structure alone doesn't guarantee meaningful coverage growth — same deliberate trade-off as ADR-024, not an oversight.
