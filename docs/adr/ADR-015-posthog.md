# ADR-015: Analytics and feature flags with PostHog

- **Status**: accepted
- **Date**: 2026-09-24
- **Deciders**: echimine
- **Tags**: analytics, feature-flags, posthog, gdpr

## Context

We need to understand how the app is used (activation, retention, user journeys), turn features on or off remotely, and run product A/B tests (ADR-016). Constraints:
- data hosted **in the European Union**;
- compliance with the **GDPR** (consent, no unnecessary personal data);
- no heavy infrastructure to operate on the VPS.

## Decision

We use **PostHog Cloud EU** for product analytics, feature flags and experiments.

### Event sources

| Source | SDK | Events |
|---|---|---|
| **Mobile** | `posthog-ios` (Swift Package Manager) | Behavior: screens, actions, onboarding, paywall viewed, flag reads |
| **Backend** (`api`, `worker`) | `posthog-node` | Events that must be reliable: `activity_processed`, `activity_failed`, `subscription_started`… (ADR-014) |
| Backoffice | — | No events (internal tool) |

The backend is the source of "source of truth" events: they do not depend on the app (closed before sending, offline for a long time).

### Identity

- Before sign-in: anonymous identifier generated by the SDK.
- After sign-in: `identify(userId)`, **same identifier** as our database and RevenueCat. PostHog links the anonymous history to the account.
- On sign-out: `reset()`.
- The backend sends its events with the same `userId` as `distinct_id`.

### Data sent

- **No personal data**: no email, name, GPS coordinates, route or photo.
- Useful, non-identifying properties: sport type, rounded distance, platform, app version, premium status.
- Session recording (session replay) **disabled**: screens display maps and personal places.

### Event naming and catalog

- `object_action` format in snake_case, in the past tense: `activity_recorded`, `activity_uploaded`, `paywall_viewed`, `onboarding_completed`.
- **Typed** catalog: on the backend in `packages/contracts` (name and properties in Zod), on iOS in an `enum AnalyticsEvent`. No free-form strings in the code.

### Feature flags

- Read on the phone by the SDK, **cached**: the app works offline with the last known value.
- Each flag has a **default value in the code** (the current behavior), used if PostHog does not respond.
- On the backend: `posthog-node` with **local evaluation** (flag definitions downloaded periodically), with no network call per request.
- Uses: progressive rollout, kill switch, A/B tests (ADR-016).

### Architecture

- iOS (ADR-007): `AnalyticsClient` and `FeatureFlags` protocols in `Core/`, PostHog implementation in the infrastructure, wired in `Di.swift`. Features never import the PostHog SDK. In tests: fake implementations.
- Backend: an `analytics` module in `packages/core`, used by `api` and `worker`, which wraps `posthog-node`.

### Consent (GDPR)

- On first launch, the app asks for consent to audience measurement. **Until it is given, the SDK is in opt-out mode** (`optOut`): no events are sent.
- The choice can be changed in the app settings.
- Feature flags work without consent (no tracking); only experiment exposure measurements depend on consent.
- No cross-app tracking: Apple's App Tracking Transparency prompt is not needed.

## Alternatives Considered

| Option | Why rejected |
|---|---|
| Self-hosted PostHog on the VPS | Very heavy (ClickHouse, Kafka…) for a small VPS |
| Firebase Analytics + Remote Config | Data at Google in the United States, less flexible A/B tests, two tools |
| Mixpanel / Amplitude | No feature flags integrated to the same level, EU hosting more limited or paid |
| Separate flags tool (LaunchDarkly, Unleash) | Two tools to connect; PostHog combines analytics, flags and experiments |
| Analytics from mobile only | Critical events lost if the app is closed or offline for a long time |

## Consequences

### Positive
- A single tool to measure, toggle remotely and experiment.
- Data in the EU, with no infrastructure to manage.
- Reliable critical events thanks to the backend.
- Shared identity with RevenueCat: revenue and usage can be analyzed together.

### Negative / Risks
- **Consent**: some users will refuse, so the numbers underestimate real usage.
- **Cost**: generous free tier, then billing by volume of events and flag requests. Check the pricing and monitor volumes.
- **Flag debt**: each flag must be removed from the code once no longer needed (rules in ADR-016).
- **Catalog to keep up to date** on both sides (Zod and Swift).
